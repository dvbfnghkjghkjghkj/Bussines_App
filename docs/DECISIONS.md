## ADR-0001: Одностраничный формат и персонализация через config/company.json

- **Дата:** —
- **Статус:** принято
- **Контекст:** Приложение делается под конкретную компанию, но клиентов
  несколько. Копировать код под каждого клиента — дорого и ведёт к расхождению
  версий. Многостраничность увеличивает срок и стоимость без пользы для
  сценария «показать услуги и принять заявку».
- **Решение:** Одна страница, один пользовательский сценарий. Все данные
  компании (название, логотип, контакты, Telegram, услуги и уровни мастеров)
  выносятся в `config/company.json`. Код не знает о конкретном клиенте.
- **Альтернативы:**
  - отдельная кодовая база на клиента — дорого в поддержке, отклонили;
  - CMS с админкой — платная подписка, противоречит ограничению бюджета;
  - генерация страниц из шаблона на билде — сложнее отладка, отложили.
- **Последствия:** новый клиент = правка `company.json` и контента, без
  изменения логики. Схема `company.json` становится контрактом: её изменение
  требует правок в коде и тестах. Нужна валидация конфига при загрузке.

## ADR-0002: Android через Capacitor, а не TWA и не нативный Kotlin

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Нужна Android-версия той же одностраничное приложения и APK для
  передачи клиенту. Бюджет — только на нейросеть: платный хостинг, подписки и
  серверная инфраструктура исключены. Команда — один разработчик с агентом.
- **Решение:** Capacitor 8. `dist/` копируется в `android/app/src/main/assets/public`,
  страница открывается в WebView с `https://localhost`. Один код, офлайн-работа,
  доступ к нативным API при необходимости. `appId`, имя приложения и версия
  генерируются из `config/company.json`.
- **Альтернативы:**
  - TWA (Bubblewrap) — тонкая обёртка вокруг опубликованного сайта: нужен
    хостинг и постоянный интернет, офлайн не работает, данные компании
    отдельно от сборки; отклонили;
  - нативный Kotlin/Compose — дублирование вёрстки и логики, сроки ×2,
    для одной страницы не оправдано; отклонили;
  - React Native — тот же минус плюс смена стека; отклонили.
- **Последствия:** `android/` живёт в репозитории, обновление Capacitor требует
  прогона сборки. WebView на старых устройствах может отставать по CSS —
  минимум `minSdk 24` (Android 7), проверять на реальном телефоне. Появляется
  зависимость от Gradle/JDK в CI, но не на машине разработчика.

## ADR-0003: Заявки из APK по deep link, без токена бота в бинарнике

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Отправка заявок в Telegram через Bot API требует токена. Любой
  секрет, зашитый в APK, извлекается из архива за минуту (`strings`, `unzip`),
  после чего бот доступен злоумышленнику: спам, подмена получателя, блокировка.
  Серверная прослойка требует хостинга, а бюджет — только на нейросеть.
- **Решение:** APK открывает `tg://resolve?domain=<ник>&text=<заявка>` — чат
  компании с заполненным текстом. Web открывает `https://t.me/<ник>?text=<заявка>`
  — тот же чат владельца (share-ссылка `t.me/share/url` отвергнута: она даёт
  клиенту выбрать любого адресата, а нужен именно чат компании).
  Токен бота в клиентских сборках не используется; `.env` остаётся для
  возможной серверной прослойки в будущем.
- **Альтернативы:**
  - токен в APK — недопустимый риск утечки; отклонили;
  - токен вводит владелец в настройках приложения — лишний шаг для клиента,
    токен всё равно лежит на устройстве; отложили;
  - Cloudflare Workers/серверлесс-прокси — работоспособно, но третий аккаунт
    и внешняя зависимость; отложили до появления реальной необходимости.
- **Последствия:** заявка не отправляется автоматически — пользователь нажимает
  «Отправить» в Telegram. Нужен заполненный `contacts.telegram` у клиента.
  Если Telegram не установлен, текст копируется в буфер обмена. Статистику
  доставки заявок так не собрать — при необходимости вернуться к прокси.

## ADR-0004: APK собирается в GitHub Actions, локальные JDK/SDK не обязательны

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** На машине разработки нет JDK и Android SDK, установка занимает
  несколько гигабайт и требует настройки `ANDROID_HOME`. Нужен воспроизводимый
  способ получать APK на каждую версию.
- **Решение:** Workflow `android-apk.yml` на `ubuntu-latest`: Node 20, JDK 21,
  кэш Gradle, `assembleDebug` → артефакт; при наличии secrets — `assembleRelease`
  с подписью. Локальная сборка (`npm run android:apk`) остаётся опцией для тех,
  у кого стоит Android Studio.
- **Альтернативы:**
  - только локальная сборка — требует установки инструментов и ломает
    воспроизводимость; отклонили как основной путь;
  - сторонние сборщики APK — платно/непрозрачно; отклонили.
- **Последствия:** APK доступен как артефакт Actions, ссылка живёт 90 дней.
  Для Google Play нужен аккаунт разработчика (единоразово, вне бюджета проекта).
  Секреты подписи хранятся в GitHub Secrets, keystore — вне репозитория.

## ADR-0005: Обход `spawn EPERM` в песочнице DSH на Windows

- **Дата:** 2026-11-09
- **Статус:** принято (локальная особенность, не архитектура продукта)
- **Контекст:** Vite на Windows вызывает `net use` для проверки сетевых дисков,
  а Vitest по умолчанию поднимает форк-процессы. Песочница DSH запрещает
  дочерние процессы с pipe-каналами — сборка и тесты падают с `spawn EPERM`.
- **Решение:** скрипты запускают Vite и Vitest с `--configLoader native`
  (конфиг читается нативно, без бандлинга и realpath-проверки), в конфиге
  Vitest задан `pool: 'threads'` вместо форков. В CI на Linux поведение
  не меняется.
- **Альтернативы:**
  - запускать всё с `danger-full-access` — снимает ограничение песочницы,
    но требует подтверждения на каждую команду; отклонили как постоянный режим;
  - патчить `child_process` через preload — хрупко, ломает инструменты; отклонили.
- **Последствия:** в скриптах появились флаги, которые вне песочницы безвредны.
  Если Vite уберёт `--configLoader`, скрипты придётся поправить. Тесты в пуле
  потоков не изолированы процессами — для нашего набора (чистые функции) это
  не проблема, но при появлении тестов с глобальным состоянием стоит вернуться
  к форкам в CI.

## ADR-0006: ПК-версия — Electron + установщик Inno Setup

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Нужен установочный файл для Windows. В прошлых проектах уже
  использовался Inno Setup 6: установка без прав администратора в
  `%LOCALAPPDATA%\Programs`, русский мастер, ярлыки. На машине разработки нет
  Rust и dotnet, зато есть Node и WebView2.
- **Решение:** страница собирается в `dist/`, Electron-оболочка грузит её
  через `file://`, electron-builder делает `release/win-unpacked`, Inno Setup
  упаковывает папку в `<appId>-setup-<версия>.exe`. Имя, appId и версия берутся
  из `config/company.json` — как у Android.
- **Альтернативы:**
  - Tauri 2 — установщик в 10 раз меньше, но требует Rust (~1,5 ГБ) и сборку
    дольше; отклонили на текущем этапе;
  - electron-builder NSIS — проще (одна команда), но даёт другой вид
    установщика и расходится с конвенциями прошлых проектов; отложили;
  - portable exe без установки — нет ярлыков и удаления через «Программы»;
    не подходит под формулировку «установочный файл».
- **Последствия:** установщик ~85–110 МБ, без подписи Windows покажет
  «Неизвестный издатель». Обновление Electron требует пересборки. Зато один
  UI-код и предсказуемая установка на уровне остальных проектов.

## ADR-0007: Демо — отдельная сборка с флагом и публикация на GitHub Pages

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Клиенту нужно показать страницу до передачи файлов. Демо должно
  жить по ссылке, обновляться без ручной выгрузки и не путаться с продакшеном.
  Бесплатный хостинг уже есть — GitHub Pages в рамках Actions.
- **Решение:** режим Vite `demo` подставляет `__DEMO__ = true`. Страница
  показывает плашку «Демо-версия», отключает отправку заявки и скрывает ссылку
  на Telegram. `npm run build:demo` кладёт сборку в `dist-demo`, workflow
  `pages-demo.yml` публикует её на Pages при пуше в `main`.
- **Альтернативы:**
  - отдельный демо-конфиг с вымышленной компанией — клиент выбрал вариант
    «данные клиента, но с плашкой»; держим в уме как следующий шаг;
  - ручная выгрузка по FTP — медленнее и требует доступов; оставлена как
    запасной путь, `dist-demo` — обычная статика.
- **Последствия:** демо публично (Pages не умеет приватность) — секретов там
  быть не должно. Демо и продакшен используют один `company.json`, поэтому
  правка конфига меняет обе версии. Ветка `main` становится «витриной»:
  сломанный пуш ломает демо, поэтому проверки в CI обязательны.

## ADR-0008: Установка Electron в песочнице — `--ignore-scripts` и кэш в проекте

- **Дата:** 2026-11-09
- **Статус:** принято (локальная особенность окружения)
- **Контекст:** `npm install` падает на postinstall `electron-winstaller`
  (`spawn EPERM`), а `electron/install.js` не может писать в
  `%LOCALAPPDATA%\electron` и игнорирует `ELECTRON_CACHE`.
- **Решение:** ставим пакеты с `--ignore-scripts`, бинарник Electron докачиваем
  вручную: `electron_config_cache=<папка проекта>` + `node node_modules/electron/install.js`.
  Кэш и `node_modules` лежат внутри рабочей папки, поэтому песочница их пускает.
- **Альтернативы:**
  - запуск `npm install` с полным доступом к диску — снимает ограничение
    песочницы, но требует подтверждения и даёт агенту лишние права; отклонили;
  - отказаться от локальной проверки Electron — тогда конфиг уезжает в CI
    непроверенным; отклонили.
- **Последствия:** в README и STATE описаны две команды вместо одной. В CI
  (Linux/Windows-раннеры) обычный `npm install` работает штатно, обход нужен
  только на машине разработки под DSH.

## ADR-0009: Шаблон переориентирован с аренды техники на сферу услуг

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Первый клиент — барбершоп OldBoy (Тверь). Исходная схема
  описывала аренду техники: единица техники, ставка ₽/час, минимальная смена,
  зоны доставки. Для барбершопа это не имеет смысла: нет ни смен, ни доставки,
  а заявка «стрижка × 4 часа» выглядит абсурдно. Одновременно нужен был
  универсальный шаблон, а не одноразовая страница.
- **Решение:** Модель заменена на услуги: `services[]` (id, name, duration,
  цена `price` или карта `prices` по уровням) и `levels[]` (Барбер / ТОП /
  ПРЕМИУМ). Цена в карточке показывается диапазоном, в форме — точной для
  выбранного уровня. Блок «Доставка» заменён на «Как найти» (адрес, вход,
  часы, телефон). `deliveryZones`, `machines`, `ratePerHour`,
  `minShiftHours` удалены из конфига и кода.
- **Альтернативы:**
  - оставить модель аренды и вписать барбершоп как «услуги без доставки» —
    быстро, но в форме остаются бессмысленные поля; отклонили;
  - отдельная ветка шаблона под сферу услуг — дублирование кода и тестов;
    отклонили.
- **Последствия:** смена схемы `company.json` — контракт проекта обновлён
  (валидация, тесты, документация). Новый клиент-барбершоп подключается
  правкой конфига. Позже аренда вернулась вторым типом шаблона (ADR-0011),
  так что сфера услуг осталась отдельной схемой, а не единственной.

## ADR-0010: Package id и имя exe не выводятся из одного поля

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** `appId` вида `ru.oldboy.barbershop` давал последний сегмент
  `barbershop` как имя exe, а Android-класс `MainActivity` лежал в пакете
  `ru.example.businessapp`. При смене `appId` приложение падало бы при запуске:
  манифест искал `.MainActivity` в новом namespace.
- **Решение:** имя exe берётся из `app.exeName` (латиница), иначе — последний
  сегмент `appId`; логика продублирована в `electron-builder.config.cjs` и
  `scripts/build-installer.mjs`. `scripts/gen-android-config.mjs` при смене
  `appId` переносит `MainActivity.java` в папку нового пакета, правит
  объявление `package` и убирает опустевшие каталоги.
- **Альтернативы:**
  - жёстко задать имя exe в конфиге electron-builder — расходится с Android и
    вводит второй источник правды; отклонили;
  - оставить `ru.example.*` в проде — неприемлемо для клиента.
- **Последствия:** переименование `appId` теперь безопасно и проверяется
  скриптом; дублирование `resolveExeName` в двух файлах нужно держать
  синхронным (отмечено комментариями).

## ADR-0011: Два типа шаблона — `services` и `rental`

- **Дата:** 2026-11-09
- **Статус:** принято
- **Контекст:** Кейс из `knowledge/идея.txt` — 13 продаж по 70 $ в нише
  аренды спецтехники: каталог с фото, ставка ₽/час, минимальная смена,
  доставка по зонам, статус «занята». Первый реальный клиент — барбершоп,
  которому нужны услуги по уровням мастеров. Держать два репозитория ради
  двух ниш противоречит цели «один шаблон = быстрая персонализация».
- **Решение:** в `config/company.json` появилось поле `template`:
  `services` (услуги, уровни мастеров, длительность) или `rental` (техника,
  ставка, минимальная смена, зоны доставки, статус). Секции страницы и поля
  формы переключаются по типу; модель цен общая по идее «предварительный
  диапазон»: в услугах — по уровням, в аренде — от минимальной смены до
  запрошенных часов плюс доставка. Обе схемы проверяются валидацией и тестами,
  образец аренды лежит в `config/examples/rental.json`.
- **Альтернативы:**
  - оставить только услуги — теряем валидированную нишу из кейса; отклонили;
  - два отдельных проекта — двойная поддержка и расхождение версий; отклонили;
  - параметризовать всё подряд (произвольные поля) — превращается в конструктор
    и убивает скорость персонализации; отклонили.
- **Последствия:** у конфига два контракта, документация описывает оба.
  Третий тип (например, доставка еды) потребует нового рендера, но не нового
  проекта. Демо и продакшен по-прежнему собираются из одного `company.json`;
  переключение ниши — правка `template` и данных.

## ADR-0012: Панель владельца на localStorage, три статуса техники

- **Дата:** 2026-11-10
- **Статус:** принято
- **Контекст:** Референс кейса (скриншоты СТРОЙМАШ, Екатеринбург) содержит
  страницу «УПРАВЛЕНИЕ ПАРКОМ»: владелец меняет цену за час, минимальную
  смену и статус техники, а клиентская страница сразу пересчитывает
  стоимость. ТЗ разрешает простую панель владельца, но запрещает сервер,
  базу данных и личный кабинет. Статусов в референсе три: «Свободна»,
  «Занята», «Требует подтверждения». Доставка — фиксированная цена зоны.
- **Решение:** панель живёт по адресу `#owner` в том же приложении. Правки
  хранятся в `localStorage` браузера владельца (`stroymash:park:v1`), при
  загрузке накладываются на технику из конфига; сброс возвращает значения
  конфига. Занятая техника не выбирается, «требует подтверждения» —
  выбирается, но помечается в заявке и в чате. Доставка считается как
  фиксированная цена зоны, без порогов.
- **Альтернативы:**
  - сервер + база — прямое нарушение ТЗ «самый простой вариант»; отклонили;
  - редактирование `config/company.json` из браузера — файл статический,
    записать его нельзя; отклонили;
  - правки в URL-параметрах — ссылки разъезжаются, состояние теряется; отклонили.
- **Последствия:** владелец видит свои изменения только в своём браузере;
  чтобы их увидели клиенты, данные переносятся в конфиг и публикуются заново
  (об этом честно сказано в панели). Для одного филиала и одной страницы
  этого достаточно; при нескольких менеджерах понадобится сервер — осознанный
  долг, зафиксирован в STATE.
