# feature-dev — разработка фичи по TDD

## Когда применять

Пользователь просит добавить, изменить или починить функциональность
приложения: новый блок на странице, расчёт стоимости, валидацию формы,
отправку заявки, работу с `config/company.json`.

## Workflow

### 1. Прочитать контекст

- `docs/STATE.md` — что уже сделано, что в работе, какие решения приняты.
- `docs/CONVENTIONS.md` — структура папок, нейминг, ветки, коммиты.
- `config/company.json` — какие данные доступны (если фича про данные компании).
- `docs/PROJECT.md` — ограничения: одна страница, цена диапазоном, бюджет
  только на нейросеть.

Если требование противоречит ограничениям проекта — скажи об этом до начала
работы, а не после.

### 2. Сформулировать ожидаемое поведение

Опиши фичу как сценарий **Given-When-Then**:

```
Given компания с тарифом 1800 ₽/час и минимальной сменой 4 часа
When пользователь выбирает 3 часа
Then стоимость считается как 4 часа = 7200 ₽
```

Уточни границы: что считается ошибкой, что — краевым случаем, что явно
вне задачи. Один сценарий — один тест.

### 3. Написать падающий тест и убедиться, что он падает

- Юнит-тест — в `tests/unit/<модуль>.test.js`.
- Запусти `npm test` и убедись, что новый тест **красный по нужной причине**
  (не «модуль не найден» из-за опечатки в пути).
- Не пиши реализацию до красного теста.

### 4. Сгенерировать реализацию

- Минимальный код, который делает тест зелёным.
- Данные компании — только из `config/company.json`, без хардкода.
- Нейминг по `docs/CONVENTIONS.md`.
- Если решение архитектурное — зафиксируй в `docs/DECISIONS.md`.

### 5. Прогнать тесты по нарастающей

1. `npm test` — юнит и интеграционные.
2. Property-based тесты (`fast-check`) для граничных случаев: нулевые и
   отрицательные значения, максимальные смены, пустые массивы, отсутствующие
   поля конфига, нечисловые строки.
3. `npm run test:e2e` — полный сценарий пользователя в браузере.
4. `npm run lint` — стиль.

Падающий тест — стоп-сигнал. Чини причину.

### 6. Обновить `docs/STATE.md`

- «Сделано» — что готово и чем проверено.
- «В работе» — что осталось незакрытым (или очистить раздел).
- «Осталось» — новые задачи, выросшие из работы.
- «Решения» — если появилось решение, влияющее на дальнейший код.

### 7. Не «заметать» падающие тесты

Запрещено: удалять тест, ставить `skip`/`todo`, ослаблять ассерты, расширять
допуски, комментировать проверку — ради зелёной сборки. Если тест падает
из-за неверного требования — исправь требование явно и объясни почему.
Если не уверен — спроси пользователя.

## Критерии готовности

- Есть тест, который был красным и стал зелёным.
- Покрыты граничные случаи (property-based) и основной сценарий (E2E).
- `npm test`, `npm run test:e2e`, `npm run lint` — зелёные.
- Данные не захардкожены, конфиг остаётся единственным источником.
- `docs/STATE.md` обновлён.

## Чего не делать

- Не начинать с кода «потом тесты допишу».
- Не трогать `knowledge/` без подтверждения.
- Не добавлять роутер и вторую страницу.
- Не коммитить `.env` и токены.
- Не менять публичный формат `config/company.json` без обновления тестов
  и `docs/DECISIONS.md`.
