# knowledge-review — разбор папки знаний

## Когда применять

Пользователь говорит «изучи knowledge», «что в папке знаний», «посмотри
материалы», «что у нас есть по нише/ценам/конкурентам» — или просит понять,
каких данных не хватает для заполнения `config/company.json`.

## Что нужно на входе

- Папка `knowledge/` с файлами (`.md`, `.txt`, `.json`) в подпапках
  `niches/`, `pricing/`, `competitors/`, `templates/`, `notes/`.
- Если папка пуста или содержит только `README.md` — так и скажи, не выдумывай
  содержимое.

## Workflow

### 1. Прочитать все файлы

Пройди рекурсивно по `knowledge/` и прочитай **все** файлы Markdown, TXT и JSON.
Файлы `README.md` — инструкция, а не источник данных: не считай их материалом.
Для каждого файла запомни: путь, о чём он, к какой нише/бизнесу относится.

Если файлов много (больше ~15), сначала составь список, затем читай по
подпапкам, чтобы не потерять структуру.

### 2. Сделать краткое резюме

Ответь на вопросы:

- Что за информация лежит в папке (типы материалов, объём)?
- Для какой ниши / бизнеса / города эти материалы?
- Насколько они пригодны для текущего проекта (см. `docs/PROJECT.md`)?
- Чего в материалах нет вообще, а что есть в избытке?

Резюме — 5–10 строк. Без пересказа каждого файла.

### 3. Предложить 3–5 конкретных действий

Три категории, в каждой — конкретика, а не общие слова:

1. **Использовать в текущем проекте** — что из прочитанного сразу идёт
   в работу (тексты, структура оффера, диапазоны цен для отображения).
2. **Перенести в `config/company.json`** — какие именно поля и какие значения:
   `companyName`, `contacts.phone`, `deliveryZones[]`, `machines[].ratePerHour`
   и т. д. Указывай значение-кандидат и файл-источник.
3. **Добавить в `knowledge/`** — каких данных не хватает и какой файл завести:
   например `pricing/2026-11-arenda-ceny.md`, `competitors/konkurenty-gorod.md`.

Плюс отдельным пунктом, если уместно: **вопросы клиенту** — что уточнить,
чтобы закрыть пробелы.

Формат:

```
1. [Проект] Взять структуру оффера из niches/arenda-spectehniki.md → блок «Услуги».
2. [config/company.json] machines[0].ratePerHour = 1800 — из pricing/prays-list.md.
3. [knowledge/] Не хватает зон доставки — завести pricing/dostavka-zony.md.
```

### 4. Не изменять `knowledge/` без подтверждения

Ничего не создавай, не переименовывай, не «причёсывай» и не удаляй
в `knowledge/` — даже если файл явно устарел. Сначала покажи предложение,
дождись подтверждения, только потом действуй. То же касается
`config/company.json`: предложить значения можно, записать — после согласия.

### 5. Записать выводы в `docs/STATE.md`

Обнови раздел **«Knowledge review»**: дата, краткое резюме, список
предложенных действий, что подтверждено и что осталось без ответа.
Раздел «Осталось» дополни задачами, которые выросли из разбора.

## Критерии готовности

- Прочитаны все файлы (или явно сказано, что папка пуста).
- Резюме отвечает «что это и для кого».
- Есть 3–5 конкретных действий с путями и полями.
- `knowledge/` не изменён.
- `docs/STATE.md` обновлён.

## Чего не делать

- Не выдумывать данные, которых нет в файлах.
- Не переносить в `config/company.json` цифры без источника.
- Не превращать разбор в пересказ каждого файла.
- Не молчать о противоречиях между файлами — покажи их явно.
